# Уведомления TIBON через ВКонтакте и MAX

Worker читает существующую очередь Outbox и отправляет уведомления в один канал. В сообщении есть ID заявки, формат, время поступления по Ижевску и статус заявки. Контактные данные, комментарий и ключ PDF остаются в закрытой системе TIBON.

Для обработки обратного звонка администратору понадобится доступ к контактам по ID заявки. До переключения определите, кто будет смотреть заявки через закрытый интерфейс с авторизацией или через уполномоченного сотрудника с защищённым доступом на чтение. Публичного интерфейса для поиска заявок по ID в этом релизе нет. Согласуйте текст политики обработки данных с ответственным за неё перед публикацией.

## ВКонтакте

1. Войдите под аккаунтом владельца или администратора и откройте сообщество TIBON. В меню сообщества нажмите **Управление**, затем **Сообщения**. Включите сообщения сообщества.
2. В разделе управления откройте **Работа с API → Ключи доступа → Создать ключ**. Разрешите доступ к сообщениям сообщества. Для отправки используется ключ сообщества с правом `messages`. [Схема VK API для messages.send](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json)
3. Для личного получателя попросите его написать сообществу с нужного аккаунта и разрешить сообщения. В сообщениях сообщества можно взять числовой ID его профиля. Для беседы добавьте сообщество в неё, если настройки VK и беседы это разрешают, и убедитесь, что сообщество может писать. Вызовите `messages.getConversations` с ключом сообщества и найдите `response.items[].conversation.peer.id` нужного диалога. Для беседы это полный `peer_id` вида `2000000000 + chat_id`. Используйте ID из ответа API, чтобы выбрать нужный диалог. [Схема методов VK API](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json)
4. Запишите ключ в `VK_COMMUNITY_TOKEN`, числовой ID в `VK_PEER_ID` и выберите `NOTIFICATION_PROVIDER=vk`. Место хранения настроек на сервере описано ниже.
5. Сначала укажите закрытый тестовый диалог или получателя, который ожидает проверку. Запустите `python -m app.notifications test-send` из `backend/` в окружении приложения. Команда отправит одно сообщение с фиксированным тестовым текстом и обойдётся без подключения к БД. Проверьте, что оно пришло именно в ожидаемый диалог. Если видите `authorization`, проверьте ключ, его разрешения и право сообщества писать адресату. [Коды ошибок VK API](https://github.com/VKCOM/vk-api-schema/blob/master/errors.json)

## MAX

1. Войдите на платформу MAX для партнёров и создайте верифицированный профиль российского юрлица, ИП или самозанятого. Для подтверждения юрлица или ИП через Госуслуги потребуется роль руководителя или администратора. [Верификация профиля](https://dev.max.ru/help/organization/)
2. В разделе **Чат-боты** нажмите **Создать**, заполните описание бота и дождитесь модерации. Откройте **⋮ → Настройки** одобренного бота и скопируйте токен. Его также можно получить через мини-приложение «MAX для бизнеса», если бот оформлен там. [Создание и модерация](https://dev.max.ru/docs/chatbots/bots-create/create/), [токен](https://dev.max.ru/docs-api/methods/POST/messages)
3. В настройках бота откройте **Приватность** и разрешите добавлять его в групповые чаты. В MAX откройте закрытый рабочий чат, добавьте бота через список участников и назначьте его администратором, как требует MAX для отправки в групповой чат. Оставьте только необходимые права. [Добавление бота и права](https://dev.max.ru/docs/chatbots/bots-coding/prepare/)
4. Для первоначального получения ID воспользуйтесь `GET /updates` с `types=bot_added` в тестовом окружении бота. Получите событие добавления в нужный чат и скопируйте `chat_id` со знаком, если он отрицательный. Если событие уже прошло, повторите добавление в согласованное время либо возьмите ID из события существующего webhook. Для бота с действующим webhook используйте его события без переключения на Long Polling. Worker использует ID из конфигурации и не подписывается на события. [Получение ID чата](https://dev.max.ru/docs-api/methods/GET/chats), [GET /updates](https://dev.max.ru/docs-api/methods/GET/updates/)
5. Запишите токен в `MAX_BOT_TOKEN`, ID в `MAX_CHAT_ID` и задайте `NOTIFICATION_PROVIDER=max`. API работает на `platform-api2.max.ru`. Загрузите доверенный сертификат Минцифры из официального источника, сохраните PEM в закрытом каталоге настроек и укажите абсолютный путь в `MAX_CA_FILE`. Если сертификат уже входит в используемый HTTPX набор доверенных CA, указывать путь необязательно. Проверка TLS обязательна. [Изменения MAX API](https://dev.max.ru/docs-api/changelog-api/), [сертификаты Минцифры](https://www.gosuslugi.ru/crt)
6. В закрытом тестовом чате выполните `python -m app.notifications test-send` и убедитесь, что получили сообщение. При ошибке авторизации проверьте токен. При отказе API проверьте модерацию, включение групповых чатов, ID и права бота. [Отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages)

## Beget VPS

В [infra](infra/) есть пример шлюза NGINX и Compose-файл с одним сервисом PostgreSQL. Команда Worker в репозитории — `python -m app.notifications run`. Реальный менеджер процессов и пути на VPS в репозитории не указаны. Перед выкладкой ответственный за VPS должен определить способ запуска Worker и SSR.

1. На VPS найдите PID текущего Worker командой `pgrep -f 'app[.]notifications run'`. Для найденного PID посмотрите родительский процесс через `ps -o pid,ppid,comm -p PID`, рабочий каталог через `readlink /proc/PID/cwd` и принадлежность к службе или контейнеру через `cat /proc/PID/cgroup`. Если Worker не запущен или команда запуска отличается, посмотрите учётную запись и настройки запуска у администратора VPS. Уточните также команду управления SSR. Храните секреты в фактически используемом защищённом окружении Worker или в корневом `.env` релиза с доступом только для владельца процесса. Переменные процесса имеют приоритет перед `.env`. Держите `.env` вне публичного каталога и Git.
2. Подготовьте новый релиз в отдельном каталоге и соберите frontend командой `npm ci`, затем `npm run build` из `frontend/`. Выполните `test-send` в отдельном тестовом окружении с закрытым получателем. Оставьте текущие подключение FastAPI к PostgreSQL, каталог приватных PDF и параметры прокси. В этом релизе нет миграций. Таблица `telegram_notifications` сохраняет своё историческое имя ради совместимости. Копирование или сброс БД для выкладки не требуются.
3. Перед остановкой старого Worker проверьте очередь командой `python -m app.notifications status` в его окружении. Дождитесь завершения активной доставки и убедитесь, что старый процесс остановлен. Если после аварийной остановки остались строки `sending`, сначала сверяйте их с предыдущим каналом. По одной записи используйте `status --lead-id UUID`. `sent` остаются отправленными, `failed` требуют явного повтора, а ожидающие `pending` продолжат обработку выбранным каналом. Команда `retry --lead-id UUID` переводит только указанную запись из `failed` в `pending`. Используйте её после проверки конкретной заявки.
4. Укажите выбранный провайдер и его пару токен/ID. Переключите frontend на новую SSR-сборку и запустите только новый Worker штатным менеджером. Если на сервере подтверждён systemd, используйте `systemctl restart ИМЯ.service` для службы Worker, `systemctl status ИМЯ.service` и `journalctl -u ИМЯ.service -n 50 --no-pager`. Если подтверждён отдельный Compose-сервис Worker, после смены окружения обновите только его командой `docker compose up -d --no-deps ИМЯ_СЕРВИСА` из фактического стека, затем проверьте `docker compose ps ИМЯ_СЕРВИСА` и `docker compose logs --tail 50 ИМЯ_СЕРВИСА`. Если Worker управляется иначе, перезапустите только его в этом менеджере с прежней учётной записью, рабочим каталогом и перенаправлением stdout/stderr. PostgreSQL и NGINX можно оставить запущенными.
5. В новых логах ищите `Notification worker started (vk)` или `(max)`, затем `Database connected`. Проверяйте `status` для счётчиков очереди и рабочий чат для подтверждения доставки. `rate_limited`, `network` и временная недоступность приводят к отложенным попыткам, `authorization` требует исправить конфигурацию или права. После переключения проверьте страницы и публичный health API. На стенде проверьте формы и обе защищённые загрузки PDF.
6. При откате остановите новый Worker и верните предыдущий релиз frontend. Для уведомлений верните проверенную конфигурацию VK или MAX и перезапустите Worker, либо временно оставьте Worker остановленным до исправления. FastAPI продолжит сохранять заявки и ставить их в Outbox. Если предыдущий Worker отправлял контакты через Telegram, автоматический откат на него возобновит эту передачу. Сохраняйте текущую БД и PDF и не сбрасывайте статусы доставки.

## Повторные попытки и расширение

VK получает один и тот же `random_id` на каждую попытку отправки одной заявки. MAX не документирует ключ идемпотентности для `POST /messages`. Если MAX принял сообщение, но ответ потерялся, повторы могут привести к дубликату. Сверяйте сообщения по ID заявки, особенно после сетевого сбоя или смены провайдера.

Для одновременной доставки в будущем понадобятся отдельные записи доставки с уникальностью по паре `(lead_id, provider)` и независимыми статусами и повторами. Два Worker с разными настройками и общей текущей очередью распределят заявки между каналами по порядку захвата.
