# Выпуск TIBON с уведомлениями VK

## Перед переключением

- Сверить редакцию политики, три согласия v2 и текст баннера с утверждёнными текстами.
- В панели Beget проверить историю автоматических копий именно этого VPS, наличие ручных снимков, предел хранения и порядок восстановления PostgreSQL. При восстановлении рабочая база должна оставаться закрытой для API и воркера, пока оператор повторно не применит действующие правила хранения и не сверит очередь уведомлений. Одна публичная справка Beget не подтверждает настройки сервера.
- Сверить очередь, схему `0005_lead_consent_version`, права на приватные PDF и состояние служб. Миграция для VK и смены версии текста не требуется.
- Скопировать действующие unit-файлы и их drop-in в доступный только root каталог. Сохранить старый релиз и `/etc/tibon/telegram.env`. Подключить drop-in VK, который сохраняет `common.env` и `app.env`. Не выводить содержимое файлов окружения.
- Остановить старый воркер, переключить `/srv/tibon/current` атомарной заменой символьной ссылки на том же файловом разделе, перезапустить API и дождаться готовности. Затем перезапустить SSR и запустить воркер с VK. PostgreSQL продолжает работать.
- Проверить HTTPS, SSR, обе версии согласия на тестовых данных, доступ к обеим разновидностям PDF и доставку VK. Публичная проверка состояния API сама по себе не проверяет доставку.

При аварии сначала остановить воркер. Откат SSR и API выполняется через предыдущий релиз. Если новый API исправен, сохранить совместимый API при откате SSR, чтобы он принимал открытые в браузерах формы v2. Прежний Telegram-воркер запускать только после проверки очереди и правомерности дальнейшей передачи. Он не различает версии согласия. Старые формы v1 и запросы без версии сохраняются в БД; при попытке уведомить VK запись отмечается `vk_consent_required` и обращение обрабатывается оператором в базе. Это отдельная очередь для ручной проверки, её не следует автоматически повторять.

## Срок хранения и обработка

- Один календарный месяц отсчитывается от `created_at` в часовом поясе студии `Europe/Samara`. Оператор отмечает закрытые заявки как `archived`, а отклонённые как `declined`. Статусы `new`, `contacted` и `confirmed` сохраняются для проверки оператором. Сейчас отдельного интерфейса ведения статусов нет. Оператор передаёт решение администратору, который выставляет статус в PostgreSQL после проверки заявки, её актуального статуса и оснований для дальнейшего хранения.
- Ежедневная проверка исключает записи с активной доставкой `pending` и `sending` и пропускает заблокированные строки. Очередь завершённой заявки удаляется каскадно вместе с заявкой. Отчёт содержит только числа. Просроченные заявки, требующие ручной проверки, разбирает Исмагилов Р. С. Он же обрабатывает досрочные запросы на уничтожение, отдельные законные сроки и оформляет подтверждение, если оно требуется.
- После переключения сохранить время из БД с явным часовым смещением в `TIBON_RETENTION_NOT_BEFORE`. Оно защищает все записи, созданные до запуска релиза. Снижение отсечки и удаление старых данных требуют отдельного разрешения.
- Установить units из `infra/systemd/` и закрытый `/etc/tibon/retention.env`. Первый ручной запуск сделать с `TIBON_RETENTION_APPLY=false`. Сверить вывод и только затем поставить `TIBON_RETENTION_APPLY=true` для новых заявок и включить таймер. Таймер запускается ежедневно в 03:30 по Самаре. Для отдельной проверки без записи можно вызвать:

      runuser -u postgres -- psql -X -q -d tibon --set=not_before='<фактическая отсечка со смещением>' --file=/srv/tibon/current/infra/lead-retention.sql

- NGINX ротирует журналы ежедневно, удерживая 14 архивов. Журнал systemd имеет собственные правила хранения. HTTP-журналы могут содержать IP и путь запроса, включая идентификатор при скачивании PDF. Тела форм в проверенных журналах не обнаружены. Резервные копии могут содержать удалённые из рабочей базы строки до истечения срока копии.
- VK API поддерживает `messages.delete`, но для адресного вызова нужны идентификаторы сообщений и права для выбранного диалога. У текущей очереди этих идентификаторов нет. Для доступных копий оператор удаляет сообщения в интерфейсе VK со стороны сообщества и получателя, проверяет исчезновение и фиксирует результат. Удаление для всех проверяется на неперсональном контрольном сообщении, если интерфейс предлагает этот вариант. Удаление с серверов VK этим не подтверждается. Уведомления старых заявок в Telegram относятся к отдельной истории и требуют отдельного разбора.
